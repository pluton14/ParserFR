# Журнал решений — ParserFR

Живая часть, новые записи сверху. Спека: `spec.md`. Циклы неопределённости: `ooda/`, `ooda_logs/`.

### [2026-09-22 12:40] Сбор в 6–10 потоков вместо 30
- Ситуация: в `parser.py` было 30 потоков; замер даёт 10 ст/с при 6 потоках и 27 ст/с при 16
- Решение: по умолчанию 8, максимум 10; 16+ не использовать
- Почему: в `robots.txt` Le Figaro 246 блоков `User-agent` с поимённым баном скрейперов — сайт следит, кто его качает. Выигрыш в сутки сбора не стоит риска быть отрезанными за неделю до защиты
- Риск: полный архив собирается ~25–42 ч вместо ~16 ч; сбор надо начинать в первый день, а не перед показом

### [2026-09-22 12:35] Корпус в SQLite, а не в managed-БД
- Ситуация: нужно хранить ~1.55 млн статей (~4 ГБ после сжатия), бюджет нулевой
- Решение: SQLite-файл на диске инстанса, тексты и токены в zlib
- Почему: отдельная БД тарифицируется, SQLite — нет. Нагрузка однопользовательская: пачечная запись при сборе, последовательное чтение при анализе
- Риск: одновременная запись из нескольких процессов не выдержит; при переезде на несколько воркеров придётся менять хранилище

### [2026-09-22 12:30] Сбор корпуса отделён от анализа словаря
- Ситуация: в десктопной версии скачивание и подсчёт слиты в один проход, поэтому правка словаря = полное перекачивание
- Решение: статья скачивается один раз в базу; словарь прогоняется по базе отдельной операцией
- Почему: доступно 22 года архива. Год корпуса — 93 тыс. статей и часы сети; пересчитывать это при каждой правке словаря физически нельзя, а лингвист будет править словарь постоянно
- Риск: появляется состояние, которого раньше не было — покрытие корпуса по дням. Нужен экран, где видно, за какие даты анализ вообще возможен

### [2026-09-22 12:25] Токены статьи хранятся рядом с текстом
- Ситуация: анализ токенизирует корпус заново при каждом прогоне
- Решение: класть в базу и текст, и готовый список токенов, оба сжатыми
- Почему: 1.55 млн статей по ~0.5 мс на токенизацию — это 13 минут на каждый прогон словаря вместо секунд
- Риск: при изменении правил токенизации токены придётся пересчитывать по всей базе; текст для этого сохранён специально

### [2026-09-22 12:20] Старт: перенос на React + FastAPI
- Ситуация: десктопный tkinter-парсер Le Figaro переносится в веб; спека закрыта, блокеров 0
- Решение: FastAPI + SQLite на бэкенде, React + Vite на фронте; логика токенизации и подсчёта переносится из `parser.py` без изменений
- Почему: смысловая начинка должна остаться прежней — результаты новой версии обязаны быть сравнимы со старыми выгрузками
- Риск: до 01.10 девять дней, из них сутки-двое занимает сбор корпуса

### [2026-09-22 12:20] Срезано: система без авторизации
- Ситуация: сервер публичный, сбор — тяжёлая операция
- Решение: авторизации нет, точки подключения оставлены
- Риск: любой, кто знает адрес, может запустить сбор и нагрузить инстанс; перед реальной передачей коллеге нужен хотя бы один общий пароль

### [2026-09-22 13:10] Платные статьи включены в анализ как есть
- Ситуация: с 2026 Le Figaro отдаёт платные статьи кодом 200 с затравкой (2-3 абзаца), а не 500 как раньше. Без детектора это тихо портит корпус: слово в скрытой части текста считается отсутствующим
- Решение: детектор `figaro._is_truncated` находит обрезанные по классам `.fig-premium-paywall`/`.fig-premium-mark-article` и фразам «réservé aux abonnés». Статус `truncated` отдельно от `ok`, но обе категории участвуют в анализе — по прямому решению пользователя («пусть будут огрызки»)
- Почему: на корпусе за 20-21 сентября обрезанных 27%; выбрасывать их значило бы терять больше данных, чем оставлять неполными
- Риск: доля обрезанных статей теперь обязана быть видна пользователю в интерфейсе (articles_truncated в CorpusSummary) — иначе решение принято молча

### [2026-09-22 13:35] Автотесты на качество данных
- Ситуация: пользователь прямо попросил не портить данные и не допустить дублей при прогонах
- Решение: 21 тест — сверка токенизатора с parser.py, подсчёт соседей и словосочетаний, идемпотентность повторного сбора (на моках, без сети), детектор обрезанных статей включая регрессию на fig-premium-mark
- Риск: тестов на реальную сеть нет намеренно — они были бы нестабильны и нарушали бы темп сбора; актуальность детектора подтверждена только живым прогоном 2026-09-22, при изменении вёрстки Le Figaro его придётся перепроверить вручную

### [2026-09-22 14:15] Фронтенд: React + Vite, три экрана
- Ситуация: нужен рабочий дашборд под показ 01.10; Node в среде разработки 16.20.2 (старый)
- Решение: Vite 4.x (поддерживает Node 16) вместо Vite 5+; React Router, без сторонней библиотеки графиков — динамика по дням нарисована как лёгкий inline SVG
- Почему: минимизировать зависимости при коротком сроке; прод-сборка в любом случае пойдёт через Docker с современным Node, локальное ограничение Node не влияет на деплой
- Риск: sparkline-график не тестировался на периодах длиннее 2 дней — форма линии при сотнях точек не проверена визуально

### [2026-09-22 14:15] Сквозная проверка: бэкенд + фронт живьём
- Ситуация: нужна уверенность, что весь путь работает, не только API по отдельности
- Решение: поднял uvicorn + vite dev, прогнал через встроенный браузер все три страницы на реальных данных (2 дня корпуса, 374 статьи, обрезанные видны отдельно, примеры подсвечиваются, экспорт JSON/HTML отдаёт файлы)
- Риск: не проверен полный цикл сбор→анализ на большом периоде (недели/месяцы) и поведение SSE-прогресса на многочасовой задаче — это стоит проверить при первом реальном запуске полного архива

### [2026-09-22 14:40] Найдено и исправлено: O(n×k) в подсчёте статистики
- Ситуация: пользователь спросил про скорость поиска на полном архиве. Замер вскрыл: наивный перебор всех ключевых слов на каждой позиции текста давал бы ~86 минут на один анализ по всему архиву (16 слов) и хуже при большем словаре
- Решение: индекс по первому слову фразы (хеш-таблица), один проход по токенам статьи вместо вложенного цикла
- Почему: множитель на размер словаря почти исчезает — то же измерение после фикса: 3.5 мин на 16 слов, 16.8 мин на ~104 слова вместо линейного роста в разы больше
- Риск: не проверено на реальном полном корпусе, только на синтетическом бенчмарке — стоит перемерить, когда архив будет собран

### [2026-09-22 14:45] Найдено и исправлено: сбор не резюмировался дёшево
- Ситуация: при перезапуске (например после выключения ПК) run_harvest заново листил ВСЕ суточные карты периода, включая уже собранные — на полном архиве это ~7700 лишних сетевых запросов при каждом рестарте
- Решение: дни со статусом done в HarvestedDay пропускаются целиком, без обращения к их sitemap, если не передан refresh=True
- Почему: пользователь прямо спросил про сохранение прогресса при выключении ПК во время многочасового сбора — без этого фикса резюме работало бы, но медленно и с лишней нагрузкой на источник
- Риск: сам сбор запускается вручную повторным вызовом того же периода — автоматического рестарта после падения процесса нет, это сознательная граница (см. AGENTS/spec.md: без авторизации, без сложной оркестрации)

### [2026-09-22 15:10] Найдено и исправлено: пауза посреди дня ломала резюме
- Ситуация: пользователь спросил, как ставить сбор на паузу. Проверка вскрыла: остановка посреди суток помечала день как done (через устаревший failed_count, читаемый сразу после отметки RUNNING), хотя часть статей не была даже начата — futures отменялись без ошибки и без записи. В связке со вчерашним фиксом резюме (пропуск done-дней) это значило бы тихую and невосстановимую потерю недобранных статей при каждой паузе
- Решение: день помечается done только если для всех его URL есть исход в базе (ok/truncated/premium/empty/failed) — проверяется свежим запросом к Article на момент решения, а не по кэшированному полю. Отменённая/недобранная часть даёт partial, что снимает пропуск при следующем запуске
- Почему: без этого «поставить на паузу» и «резюмировать» были рассинхронизированы — пауза формально работала (задача останавливалась), но резюме тихо считало день полным
- Риск: закрыто тестом на паузу+резюме (24/24 зелёных, стабильно на 15 повторных прогонах — гонки потоков не давали флуктуаций)

### [2026-09-22 15:35] Найдено и исправлено: прогресс-бар не появлялся при внешнем старте
- Ситуация: сбор архива запущен через curl напрямую (для теста), не кнопкой в интерфейсе. Страница «Корпус» не показывала прогресс-бар вообще — jobId устанавливался только в момент клика на кнопку в этой же вкладке
- Решение: страницы «Корпус» и «Анализ» при открытии опрашивают GET /api/jobs/active и сами подхватывают уже идущую задачу своего типа
- Почему: задача может быть запущена откуда угодно — с другой вкладки, по ночному расписанию, после перезагрузки страницы посреди сбора. Без этого пользователь открывает дашборд и не видит вообще ничего о многочасовой задаче, которая на самом деле работает
- Риск: не покрыто тестом (фронтенд без тестового фреймворка, см. границы объёма) — проверено вручную в браузере на реальной идущей задаче (652→669/7699 между кадрами, лог и кнопка «Остановить» отображаются)

### [2026-09-22 15:00] Запущен сбор полного архива
- Ситуация: подтверждено пользователем — полный архив 2004-2026, локально, компьютер остаётся включён
- Решение: сервер поднят на постоянных данных backend/data (не scratchpad), job_id 417f57fc-5b79-426e-ab45-58bae9c74222, диапазон уточнён до фактического 2004-12-17 — 2026-09-22 (7699 дней)
- Почему: раннее число «2004-05-05» было ошибкой моего первого ad-hoc замера (широкий regex ловил дату не там); реальная функция сбора (extract_date_from_url) стабильно даёт 2004-12-17 — на объём это не влияет
- Риск: сбор идёт 25-42 часа, компьютер должен оставаться включён и на сети всё это время

### [2026-09-22 16:05] Поправка: реальный объём архива почти вдвое больше оценки
- Ситуация: ранняя оценка ~1.55 млн статей строилась на выборке 2 дней в год (16 замеров на 22 года). Сервер, дойдя до фазы скачивания, посчитал точно по всем 7699 суточным картам: 2 795 453 статьи
- Решение: не пересчитывать заново, продолжать текущий сбор — параметры (диск, время) пользователем уже подтверждены с запасом
- Почему: точный подсчёт требовал прочитать все карты, что и произошло естественным образом на старте сбора; ничего пересчитывать заранее не было смысла
- Риск: пересмотренное время сбора ~2.5-3.5 суток вместо 25-42ч по прежней оценке; всё ещё укладывается в 9 дней до показа 01.10, но с меньшим запасом. База на диске ожидается ~12 ГБ вместо ~4 ГБ — не проблема для локальной машины, но стоит учесть при выборе диска на сервере при деплое

### [2026-09-22 15:15] Найдено и исправлено: сбой листинга тихо терял день навсегда
- Ситуация: реальный сбор поймал единичный RemoteDisconnected при чтении карты за 2015-01-04. Код превращал такой сбой в urls=[] неотличимо от дня, где статей реально нет — день попадал в ветку "done" по старой логике. В связке с резюме по дням (пропуск done-дней) это значило бы: один сетевой сбой из тысяч запросов — и день навсегда выпадает из архива без единой видимой ошибки
- Решение: отдельный флаг listing_ok на каждый день; при сбое чтения карты день помечается failed, а не done, и перечитывается на следующем запуске. Закреплено двумя тестами (сбой не даёт done; день со сбоем реально перечитывается на резюме)
- Почему: это третий баг в связке "резюме + паука по 7699 картам" за сегодня — на масштабе полного архива вероятность хотя бы одного сетевого сбоя за десятки тысяч запросов почти 100%, и без явного различения такой сбой был бы неотличим от прогала архивного дня
- Риск: закрыто тестами (26/26), но живой прогон переисправление не увидел — конкретный день 2015-01-04 не успел зафиксироваться неправильно (сбор был в фазе листинга, ничего не записано), пересобрано с чистого места с исправленным кодом

### [2026-09-22 15:00] Увеличено число потоков сбора 8 → 16 по согласованию
- Ситуация: реальный объём архива (2.8 млн статей) при 8 потоках давал ETA ~5.7 суток вместо ожидаемых 2.5-3.5 — риск не успеть к показу 01.10
- Решение: подняли до 16 потоков (2x) по замерам — умеренная эскалация вместо максимума, чтобы проверить реакцию источника прежде чем увеличивать дальше
- Почему: за все часы работы на 8 потоках источник не отдал ни одной ошибки (articles_failed: 0) — признаков активной защиты от нагрузки не было. robots.txt формально не запрещает сбор статей для generic User-Agent (запреты — для именованных ботов). Полной уверенности в поведении источника при повышенной нагрузке нет — решение явно как компромисс, не гарантия
- Риск: если источник начнёт возвращать 403/429/503 массово — откат на 8 потоков; отслеживается по articles_failed в сводке корпуса

### [2026-09-22 15:45] Найдено пользователем и исправлено: карта не кэшировалась вовсе
- Ситуация: пользователь заметил — список статей суточной карты (уже прочитанной ранее) заново запрашивался по сети при каждом перезапуске, даже для дня, ещё не докачанного полностью. За сегодня было 3 перезапуска (правки багов), и каждый раз тысячи URL уже прочитанных карт выбрасывались из памяти и читались заново
- Решение: сразу после успешного листинга URL сохраняются в Article как status=pending (заглушки — известны, не скачаны). Следующий запуск видит их напрямую в базе через _days_with_known_urls и не обращается к сети за той же картой. Новый статус ArticleStatus.PENDING
- Нюанс, пойманный пользователем при обсуждении плана: появление pending-строк сразу после листинга ломало проверку "день завершён" — она считала любую строку в базе как готовую, а pending это не скачанная статья. День мог бы ложно считаться done, не скачав ничего. Исправлено: проверка явно смотрит на pending_count==0, а не на общее число строк
- Почему: экономит тысячи сетевых запросов на каждый рестарт; на полном архиве с учётом того, сколько раз пришлось перезапускать сбор за один день разработки, это не разовая экономия, а систематическая
- Риск: закрыто 2 новыми тестами + обновлён 1 существующий (assert на "строк меньше чем urls" стал неверным семантически — заменён на "скачанных меньше чем urls"). Прогнано 10 раз подряд на гонку потоков — стабильно. Итого 28/28 тестов

### [2026-09-22 16:00] Кэш листинга: защита от частично-скачанных дней старой эры
- Ситуация: реальная база уже содержала день (2006-07-07) с частичным набором статей от самого первого прогона (до появления pending-кэша) — проверка "есть хоть одна строка" приняла бы его за полностью листингованный и потеряла бы остальные URL навсегда
- Решение: _days_with_known_urls сверяет число строк Article с total_urls, зафиксированным в HarvestedDay при последнем успешном листинге, а не просто проверяет факт существования строк. total_urls теперь пишется сразу после листинга (DayStatus.PENDING), а не только когда очередь доходит до скачивания — иначе при отмене между листингом и скачиванием сверить было бы не с чем
- Почему: без этого фикс кэша из предыдущей записи был бы небезопасен именно на данных, накопленных ДО его появления — ровно наш случай сегодня
- Риск: закрыто 4 новыми тестами (30/30, 10 прогонов подряд стабильно). День 2006-07-07 в реальной базе будет перелистан заново при следующем запуске — это единственный день, для которого кэш не сработает, дальше всё чисто

### [2026-09-22 16:15] Найдено вживую: дубль URL внутри одной суточной карты уронил сбор
- Ситуация: сбор упал с IntegrityError (UNIQUE constraint) на статье sport24.lefigaro.fr за 2009-08-26 — sitemap Le Figaro перечислил одну спортивную статью дважды внутри одной карты. Задача упала чисто (status=failed, видимая ошибка), не зависла и не испортила данные молча
- Решение: дедупликация urls сразу после листинга, до того как список пойдёт в кэш/скачивание/подсчёт. Дополнительно _persist_pending_urls защищена собственным дедупом на случай дублей из другого источника вызова
- Почему: единая точка дедупликации на входе устраняет риск во всех потребителях списка urls разом, а не патчит каждого по отдельности
- Риск: закрыто 2 тестами включая проверку total_urls по уникальным ссылкам (32/32, 10 прогонов стабильно)
